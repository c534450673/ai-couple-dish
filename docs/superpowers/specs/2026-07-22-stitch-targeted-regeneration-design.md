# Stitch 定向事务式重生成设计

## 1. 背景

Couple Cosmos 已完成 20 个本地页面 ID 的真实 Stitch 导出，严格校验确认项目归属、文件路径、SHA-256 和密钥扫描均正确。视觉复核同时发现，部分远端屏幕虽然技术上可导出，但内容偏离页面职责：Stitch 把“加载、空数据、错误、未授权和未绑定状态”误解为需要在业务页面中展示的状态组件长页，或生成了不属于该页面的内容。

本设计只修正这些生成偏差，不改变已批准的 Couple Cosmos 产品信息架构、视觉令牌或 20 个本地页面 ID。

## 2. 视觉审计结论

以下 11 个本地页面 ID 需要替换：

| 本地 ID | 主要问题 | 替换目标 |
|---|---|---|
| `home-base` | 实际为 AI 厨师推荐页 | 完整星球首页基础稿 |
| `bind` | 实际为通用推荐首页 | 邀请 TA / 输入情侣码绑定页 |
| `menu-detail` | 页面主体可用，但暴露调试状态入口 | 无调试文案的餐厅详情页 |
| `recipe-list` | 实际为系统状态组件长页 | 共同菜谱列表 |
| `recipe-editor` | 实际为系统状态组件长页 | 菜谱与餐厅渐进式编辑器 |
| `feed` | 实际为系统状态组件长页 | 情侣投喂发起和响应页 |
| `note-editor` | 更接近动态流而非编辑器 | 美食笔记编辑页 |
| `map` | 实际为地图状态说明页 | 可操作的共同足迹地图 |
| `ai-chat` | 实际为 AI 状态说明页 | 完整 AI 美食对话页 |
| `notification-center` | 实际为内容发现页 | 情侣通知中心 |
| `system-states` | 主题局限于 AI 厨师状态 | 全局统一状态组件表 |

其余页面保持现有远端引用。三个首页变体继续作为待选方案；用户选择后再对最终变体进行一次导航和文案精修，不在本次 11 屏替换中静默代选。

## 3. 方案比较

### 3.1 方案 A：第三分卷定向重新生成（采用）

在现有空闲的第三 Stitch 项目中生成 11 个新屏幕。每个屏幕成功后，以事务式 checkpoint 替换对应本地 ID 的远端引用。

优点：

- 保持 Stitch 原生截图和 HTML 的可追溯性。
- 不修改或删除旧远端屏幕，失败时可恢复。
- 第三分卷容量为 12，能够容纳全部 11 屏。
- 不影响已通过视觉复核的页面。

代价：

- 本地状态会引用三个项目。
- Stitch 远端仍保留历史错误屏幕，但它们不进入最终 manifest。

### 3.2 方案 B：编辑现有屏幕（不采用）

使用 `edit_screens` 原地修改。该方案可能延续已有错误结构，且主项目和第二分卷已接近容量或状态限制，失败恢复也更困难。

### 3.3 方案 C：手工制作本地替代资产（不采用）

手工编写 HTML 和截图会破坏“Stitch 原生设计资产”门槛，不能作为最终视觉基准。

## 4. 提示词边界

业务页面的基础提示词必须明确：

1. 生成一个完整、可操作的正常业务态移动页面。
2. 不得生成状态指南、组件表、调试画廊或多个纵向堆叠的页面变体。
3. 加载、空数据、失败、未授权和未绑定状态只能作为简短设计说明，不得替代正常业务态主体。
4. 不得显示 `DEBUG`、`UI STATES`、设计说明或实现说明等面向开发者的文案。
5. 底部导航固定为“星球、菜单、投喂、回忆、我们”。
6. 页面必须使用简体中文可见文案和 Couple Cosmos 设计令牌。

`system-states` 是唯一允许生成完整状态组件表的页面，其范围覆盖全局骨架屏、空数据、网络失败、未授权、未绑定、离线草稿、Toast、Modal 和减弱动效，而不是单一 AI 功能状态。

每个被替换页面还要包含页面专属的必须出现元素和禁止替代内容。例如，`bind` 必须同时出现“邀请 TA”和“输入情侣码”，`ai-chat` 必须出现真实对话消息、快捷问题、流式回答和写操作确认预览。

## 5. 重生成工具

新增独立的定向重生成入口，不复用“缺失页面生成”语义，也不要求先删除 state 中的旧引用。

命令接口：

```text
node bin/regenerate.mjs <local-id> [<local-id> ...]
```

入口必须：

- 只接受页面目录或 `home-base` 中的已知本地 ID。
- 拒绝空列表、重复 ID、未知 ID、`home-emotion`、`home-food` 和 `home-memory`。
- 拒绝超过当前目标分卷剩余容量的请求。
- 按参数顺序逐屏生成，支持安全断点续跑。
- 将新屏幕写入当前可写分卷，本次固定使用已登记且为空的第三分卷。
- 不打印提示词全文、API key、下载 URL 或其他敏感值。

## 6. 事务与恢复

单屏替换流程：

```text
验证目标与分卷容量
→ 记录 started 日志
→ 调用 Stitch 生成新屏幕
→ 校验非空 screenId
→ 构造只替换该 local ID 的新 state
→ 原子写入 generation-state.json
→ 记录 ok 日志
```

失败规则：

- 远端生成失败：本地 state 不变。
- 返回空 screen ID：本地 state 不变并报错。
- checkpoint 失败：保留旧本地引用；新远端屏幕可能成为孤儿，但不会污染最终 manifest。
- 前若干屏成功、后续屏失败：已成功且 checkpoint 的屏幕保留，重新执行时跳过已经属于目标分卷的目标 ID。
- 不删除旧远端屏幕，不覆盖用户未选择的首页变体。

## 7. 结构化日志

每个替换屏幕至少记录以下事件：

- `stitch.screen.regenerate` / `result=started`
- `stitch.screen.regenerate` / `result=ok`
- `stitch.screen.regenerate` / `result=error`
- 可恢复错误时记录 `stitch.screen.regenerate.retry`

字段至少包含：

- `projectId`
- `localId`
- `screenTitle`
- `attempt`
- `stage`
- `durationMs`
- `errorName` 和脱敏后的 `errorMessage`

禁止记录 API key、access token、下载 URL、完整提示词和截图内容。

## 8. 测试

单元测试覆盖：

- 未知、重复、禁止和超容量目标被拒绝。
- 只替换明确指定的本地 ID。
- 新屏幕归属第三分卷。
- 远端失败、空 ID 和 checkpoint 失败时旧引用保持不变。
- 已完成目标在断点续跑时跳过。
- 结构化日志包含开始、成功、重试和失败阶段，且不泄漏敏感信息。
- 改造后的提示词明确正常业务态优先，并仅允许 `system-states` 输出状态组件表。

真实验证覆盖：

1. 运行全部 Stitch 工具测试。
2. 经安全 PTY 和 Undici `ProxyAgent` 连接 Stitch。
3. 在第三分卷生成 11 个替换屏幕。
4. 导出精确 20 个本地页面 ID。
5. 验证 20 张截图、20 个 HTML、项目归属、SHA-256、路径安全和密钥扫描。
6. 逐页视觉复核全部 11 个替换页面，并复核三个首页变体。
7. 用户明确选择首页后，记录选择并完成最终设计资产提交。

## 9. 完成标准

本工作包只有同时满足以下条件才完成：

- 11 个目标本地 ID 均引用第三分卷中的新屏幕。
- 11 个页面的正常业务态与页面职责一致，没有可见调试或设计说明。
- `system-states` 是唯一状态组件表页面。
- state 和 manifest 仍为精确 20 个本地页面 ID。
- `login` 仍是唯一允许的 `screenshot-fallback`，其余 19 屏使用 Stitch 原生 HTML。
- 全部工具测试、严格 verifier 和视觉复核通过。
- 用户明确选择 `home-emotion`、`home-food` 或 `home-memory`。
- GitNexus 变更检测只包含预期设计工具、测试和设计资产。

## 10. 非目标

- 不在本工作包中修改 Vue H5 或后端业务代码。
- 不改变已批准的信息架构、设计令牌或商业化路线。
- 不删除 Stitch 远端历史屏幕或项目。
- 不替用户默认选择首页变体。
