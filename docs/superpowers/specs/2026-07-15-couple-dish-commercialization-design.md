# AI Couple Dish 商业化重构设计规格

> 日期：2026-07-15
> 状态：已完成章节确认，待书面规格复核
> 视觉方向：Couple Cosmos / 双人宇宙
> 客户端首发范围：frontend-h5
> 最终后端：Python 3.12 + FastAPI，不依赖 Java 运行环境

## 1. 背景与目标

AI Couple Dish 是面向情侣的私密美食与共同生活应用。现有项目已具备用户、情侣绑定、餐厅菜单、菜谱、投喂、纪念日、心愿、笔记、地图、文件上传和 AI 助手等能力，但存在以下问题：

- 当前“玫瑰奶油”视觉缺乏足够的品牌识别、空间层次和动态表现。
- H5 页面没有完整覆盖后端能力，部分路由、状态和交互链路缺失。
- 现有功能、测试和数据库脚本存在漂移，不能证明产品可商用。
- 后端基于 Spring Boot，用户明确要求最终迁移到 Python FastAPI，不再依赖 Java。
- 缺少完整的运营、隐私、监控、备份、发布和商业闭环。

本项目的最终目标是：

1. 使用 Stitch 创建完整的 Couple Cosmos 视觉设计和页面变体。
2. 在 H5 完整实现高质量、可降级、可测试的动态界面。
3. 使用 FastAPI 替代 Java 后端，并保持或改进现有业务能力。
4. 修复核心业务、权限、错误状态和数据一致性问题。
5. 建立自动化测试、真实接口测试、真实浏览器测试和视觉回归。
6. 扩展高价值情侣功能并建立可持续商业模式。
7. 达到本文定义的商用上线硬门槛后，才宣称商业化改造完成。

## 2. 已确认的关键决策

- H5 是第一个完整商业化客户端，其他客户端在 H5 稳定后再适配。
- 视觉采用 Couple Cosmos / 双人宇宙，不继续沿用现有玫瑰奶油体系。
- 底部导航采用“星球、菜单、投喂、回忆、我们”五个入口。
- 后端采用 FastAPI 模块化单体。
- MySQL 8、Redis 和同源 /api 访问方式保持不变。
- Java 后端仅在迁移期间作为行为和接口对照；最终活动后端目录、部署、CI 和运行环境只使用 Python。
- 使用详细的结构化日志，但日志不得包含敏感内容。
- AI、Stitch、JWT、数据库和其他第三方密钥只能通过运行环境注入。
- 所有设计、开发和扩展功能都必须经过自动化测试和真实浏览器验收。

## 4. 视觉方向：Couple Cosmos

### 4.1 品牌概念

应用被设计为“两个人共同经营的美食宇宙”。双方的头像、心情、计划、菜谱、餐厅和回忆都是这个宇宙中的星体与轨迹。

### 4.2 设计令牌

| 类型 | 令牌 | 用途 |
|---|---|---|
| 背景 | 深夜蓝黑与紫黑渐变 | 全局背景，不使用纯黑 |
| 主色 | #FF5D73 | 心动、食欲、主要操作 |
| 辅色 | #54E8D3 | 在线、完成、科技感 |
| 高光 | #FFC857 | 纪念日、成就、会员 |
| 卡片 | 半透明深色玻璃 | 主要信息容器 |
| 实体面板 | 高对比深色或暖白 | 表单、长文本和无障碍场景 |
| 主卡片圆角 | 24px | 列表、首页和详情 |
| 弹层圆角 | 28px | 抽屉、对话框和操作面板 |

字体使用现代中文无衬线；日期、纪念文案和关键数字可使用更具情绪感的展示字体，但不能损害正文可读性。

### 4.3 动效原则

- 首页双头像沿心形轨道缓慢运动。
- 恋爱天数与统计数字使用滚动计数效果。
- 卡片滑动产生受控的景深与视差。
- AI 助手表现为可呼吸、可拖动的发光星球。
- 投喂成功、心愿完成和情侣绑定使用星轨、粒子和心跳反馈。
- 列表图片与详情图片使用共享元素式过渡。
- 常规微交互控制在约 180ms，卡片过渡约 320ms，页面过渡约 500ms。
- 动效优先使用 transform 和 opacity；Canvas 仅用于受控的庆祝效果。
- 必须支持 prefers-reduced-motion，低性能设备自动降级。
- 动效不能改变数据提交时序、阻塞操作或导致滚动卡顿。

## 5. Stitch 设计工作流

### 5.1 接入方式

优先使用 Google Labs 作用域的 @google/stitch-sdk：

- 仓库：https://github.com/google-labs-code/stitch-sdk
- 版本在实施时锁定，不使用浮动 latest。
- 许可证为 Apache-2.0。
- 该 SDK 的 README 声明其不是 Google 正式支持产品，因此所有设计结果必须导出并纳入本地可追溯资产。

STITCH_API_KEY 仅通过当前进程环境变量提供，不写入：

- Git
- .env 示例值
- 前端包
- 测试快照
- 命令输出
- 日志
- 截图元数据

### 5.2 设计产物

Stitch 项目必须至少产出：

- 设计令牌和组件状态说明。
- 手机端登录、绑定、首页、菜单列表、菜单详情、菜谱、新增表单、投喂、回忆、地图、AI、设置页面。
- 375px、390px 和 430px 三类移动宽度的关键页面。
- 正常、加载、空数据、失败、无权限和未绑定状态。
- 至少三种首页变体，最终以 Couple Cosmos 方向收敛。
- 页面截图、HTML 导出和 Stitch 项目/屏幕 ID 清单。

导出物统一保存到 docs/design/stitch/couple-cosmos/，并生成包含项目 ID、屏幕 ID、提示词摘要、生成时间和文件哈希的 manifest.json。

## 7. 核心页面与交互

### 7.1 登录与引导

- H5 使用手机号与密码注册、登录。
- 移除不可用的微信、Apple 和伪短信入口。
- 注册完成后依次创建资料、设置恋爱日期和邀请另一半。
- 表单错误显示在字段附近，提交期间防止重复操作。
- 登录成功后恢复用户原本要访问的受保护路由。

### 7.2 情侣绑定

- 提供“邀请 TA”和“输入情侣码”两个入口。
- 情侣码展示有效期进度，支持复制、分享和重新生成。
- 绑定完成触发双头像汇合动画。
- 未绑定用户可以管理个人草稿，情侣共享能力显示明确引导。

### 7.3 星球首页

- 顶部展示双头像轨道、恋爱天数、心情和在线状态。
- 使用动态 Bento Grid 展示纪念日、心愿、投喂、菜谱和足迹。
- “今晚吃什么”提供共同偏好匹配和随机选择。
- 首页卡片独立加载、独立失败和独立重试。

### 7.4 我们的美食库

内部包含：

- 餐厅：想去、去过、种草和收藏。
- 菜谱：想做、已做、我的和 TA 的。
- 地图：当前位置和共同足迹。
- 筛选：菜系、价格、距离、难度、耗时和创建人。

新增与编辑表单支持图片上传、草稿保存、离开提醒和失败恢复。

### 7.5 投喂

- 发起时选择菜品、时间、留言和惊喜模式。
- 对方可以接受、拒绝或提出替代方案。
- 接受后生成双方可见的倒计时。
- 完成后触发庆祝，并沉淀为回忆记录。

### 7.6 回忆中心

- 纪念日、心愿、笔记和足迹整合为双人时间轴。
- 支持按年份、类型和创建人筛选。
- 纪念日使用星球公转倒计时。
- 心愿完成后从灰暗星体点亮。
- 笔记支持图片、文字、位置和关联菜谱。

### 7.7 AI 美食星球

- 全局发光星球入口，轻触打开抽屉，上滑进入完整对话。
- 支持用餐推荐、库存菜谱、约会规划和笔记整理。
- AI 写入业务数据前必须展示预览并由用户确认。
- 流式生成显示进度，断线后允许继续或重新生成。
- AI 不能绕过用户身份、情侣归属和业务 Service 校验。

### 7.8 我们与设置

- 展示情侣资料、恋爱阶段、共同统计和成长轨迹。
- 提供通知、主题、隐私、文件管理、密码修改、解绑和退出。
- 解绑需要双方确认，并明确数据归属与保留方式。

## 8. 前端架构

前端使用单向数据流：

~~~text
View
  → Feature Component / Composable
  → Pinia Feature Store
  → API Module
  → Axios Request Layer
  → FastAPI
~~~

约束：

- 页面不直接拼接 API URL，不自行处理 token。
- 用户、情侣、主题和通知使用全局 Store。
- 菜单、菜谱、投喂和回忆按功能拆分 Store。
- 组件通过明确的 props 和事件通信。
- 请求层统一处理超时、取消、去重、认证失效和响应包装。
- 首页请求允许部分成功，单个卡片失败不能拖垮整个页面。
- 动效组件与业务提交状态分离。

## 9. FastAPI 后端架构

### 9.1 技术选型

- Python 3.12
- FastAPI
- Pydantic v2
- SQLAlchemy 2
- Alembic
- MySQL 8
- redis-py 异步客户端
- pytest
- httpx
- structlog
- Uvicorn

### 9.2 目录边界

~~~text
backend/
├── app/
│   ├── api/
│   ├── core/
│   ├── models/
│   ├── schemas/
│   ├── repositories/
│   ├── services/
│   ├── ai/
│   └── main.py
├── migrations/
├── tests/
├── pyproject.toml
└── Dockerfile
~~~

职责：

- api：路由、请求校验和响应模型。
- core：配置、认证、日志、异常、限流和中间件。
- repositories：数据访问，不包含业务决策。
- services：业务规则、权限与事务边界。
- ai：外部模型、流式响应和工具调用编排。

### 9.3 数据与认证

- 初期保持现有 MySQL 表名和主要字段，降低迁移风险。
- Alembic 为现有数据库建立基线，并管理后续迁移。
- 手机号是密码账号的唯一登录标识。
- 密码使用 BCrypt 哈希，不存储或返回明文。
- JWT、会话版本和 Redis 黑名单共同支持退出及改密后失效。
- 所有情侣共享资源必须校验当前用户和情侣归属。
- 文件上传验证 MIME、文件签名、扩展名、大小和访问权限。

## 10. 结构化日志与错误恢复

### 10.1 日志字段

关键操作至少记录：

- requestId
- 脱敏用户标识
- 功能模块
- 操作类型
- 结果分类
- 耗时
- 状态码或业务错误码
- 外部依赖名称

AI 异步流程额外记录线程/任务队列状态、连接中断、首字节耗时、总耗时和取消原因。

禁止记录：

- 密码
- JWT
- 完整手机号
- Stitch 或 AI 密钥
- 私密聊天原文
- 私密笔记正文
- 上传图片内容
- 包含敏感参数的完整 URL

### 10.2 错误恢复

- 幂等查询遇到短暂网络失败时有限重试。
- 写操作超时后先查询最终状态，避免重复写入。
- Token 失效时清理会话并保存原目标路由。
- 情侣关系变化时清除情侣共享缓存并重新获取权限。
- 图片或 AI 服务失败时保留用户已填写内容。
- 数据迁移发现重复或异常数据时中止并输出脱敏统计。
- 所有用户可见错误携带可检索 requestId。

## 11. Java 到 FastAPI 的迁移

### 11.1 原则

- 不进行无法验证的“大爆炸”替换。
- 现有 Java 后端在迁移期只作为接口行为和数据规则参考。
- 当前未提交的 Java 修改不能被覆盖或丢弃。
- 最终 backend/ 活动源码、部署、CI、Docker 和运行环境只包含 Python 实现。
- 删除 Java 活动源码前，必须将当前未提交 Java 差异导出为可复核补丁并校验可读取；Git 历史继续保留原始 Java 实现。

### 11.2 顺序

1. 提取现有接口、请求模型、响应、错误码、权限和 Redis Key。
2. 建立 Java 黑盒合同测试并记录已知错误行为。
3. 建立 FastAPI 配置、日志、异常、数据库、Redis、认证和健康检查。
4. 依次迁移用户、情侣、菜单、菜谱、投喂、回忆、上传、通知和 AI。
5. 每个模块通过单元、合同和数据库集成测试后再进入下一模块。
6. H5 切换到 FastAPI 并完成浏览器主链路验证。
7. 将当前未提交 Java 差异导出为仓库外的可复核补丁，并向用户报告绝对路径与 SHA-256。
8. 从 backend/、部署入口、CI 和运行脚本中移除 Java；历史版本通过 Git 追溯，不在活动源码中保留 Java 副本。

## 14. 商业模式与运营能力
